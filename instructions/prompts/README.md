# 分阶段执行提示词

这些文件把 G00—G07 拆成可执行任务。提示词负责安排工作；[验收规范](../specs/acceptance.md)负责判据；[硬件参数](../specs/hardware-profile.json)负责实物边界；[STATUS](../STATUS.md)负责当前阶段进度。不要在提示词中另存一套阈值或阶段状态。

## 使用方法

在项目目录中直接发送：

> 读取 instructions/prompts/G01-measurement.md，按该文件推进 G01。本次先完成 G01.1—G01.3，依据已有证据继续，不重复已完成工作。

也可以请求整个阶段：

> 按 instructions/prompts/G04-pi-control.md 推进 G04，完成当前条件支持的实现和验证，将缺失的实测条件与下一动作单独列出。

复核已有结果：

> 依据 instructions/prompts/G01-measurement.md 和本次冻结的验收版本，复核现有工作卡及原始证据，逐项重算结果；指出证据不能支持的结论。

默认是继续当前阶段的探索实施。正式验收须明确本次范围，并满足 WORKFLOW 的冻结要求。只执行用户指定的阶段/子任务；整阶段请求才在条件满足时依次推进其子任务，不自动开启下一阶段。文件的存在不代表授权上电、烧录或带载，实际动作依当前会话授权和已确认条件执行；已有授权不重复询问。

## 阶段入口与任务粒度

| 提示词 | 子任务顺序 | 主要交付 |
|---|---|---|
| [G00 基线](G00-baseline.md) | 现状 → 构建身份 → 启动接口 → 硬件登记 → 复核 | 源码/固件/板卡对应关系 |
| [G01 测量](G01-measurement.md) | 通道定义 → 采集有效性 → 记录与离线检查 → 标定 → 独立验证 | 可追溯的 V/I/T |
| [G02 PWM](G02-pwm-timing.md) | 配置 → 输出/停止 → 采样时序 → 波形 → 复核 | PWM、ADC 时序及停止证据 |
| [G03 开环](G03-open-loop.md) | 台架 → 固定 D → 离线检查 → 逐点实测 → 特性分析 | D 与各端口 V/I/P 的实测关系 |
| [G04 PI](G04-pi-control.md) | 接口/反馈方向 → 算法 → 状态机 → 调参 → 正式验证 | 恒流和故障退出 |
| [G05 接口](G05-host-protocol.md) | 协议 → 解析 → 记录器 → 联调 → 并发回归 | 命令、实际动作、日志一致 |
| [G06 数据](G06-soc-dataset.md) | 参考链 → 数据处理 → 采集 → 标签 → 划分 | 可复算 SOC 标签和数据集 |
| [G07 模型](G07-model-deployment.md) | 评估契约 → 训练 → 量化 → 部署 → 回归 | 模型及端侧一致性证据 |

子任务编号是定位工作范围的标签，不是新增验收门，也不需要为每一项机械建立一个文件。已有工作卡能覆盖时继续使用；正式复测另建 run，保留旧记录。解析器、记录器、离线计算可以提前准备；台架验收仍遵守阶段依赖。

## 所有阶段共同执行的要求

每份阶段提示词均需结合本节执行：

1. 先读项目根 [AGENTS.md](../../AGENTS.md)、[项目导航](../../README.md)、[规范入口](../README.md)、[当前状态](../STATUS.md)、[工作流程](../WORKFLOW.md)及当前工作卡。读取本阶段验收条款，核对真实源码和实际纳入构建的文件。历史描述只作线索，不假定问题仍存在。
2. 把本次目标对应到验收条款/已有需求 ID，形成最小可交付范围。优先复用有效证据，说明适用版本与条件；存在变更时按 WORKFLOW 重验受影响项。
3. 按阶段提示完成已授权的实现、构建、离线检查与适用实测。合理选择验证强度；工具链或实物条件缺失只阻塞依赖它的动作，继续独立工作。需要新事实时列出具体字段、用途和获取办法。
4. 实际硬件值只维护 hardware-profile，未知保持 null。C 是课程要求，E 是待冻结工程建议，H 是实物/方案待确认；不从提示词或讲义示例推导已确认参数。
5. 探索允许迭代；正式验收前固定判据、固件、配置、标定、工况和处理方法。实际运行使用唯一 run_id，记录源码/固件身份、工具版本、仪器、时间和退出原因。
6. 使用 [工作卡模板](../templates/work-card.md)、[运行清单模板](../templates/run-manifest.json)；标定使用 [标定模板](../templates/calibration-record.json)。实际证据存放于项目根 evidence/runs/<run_id>/，raw 与 derived 分开，失败、超时和旧版本保留。模板不直接登记为已执行结果。
7. 无效、过期、PEC 错误等状态随数据传播；不填成有效零。区分 static、build、simulation、bench、release_boot；没有实测证据的结论保持未验证，verdict 不预填 pass。
8. 小任务不复制全部规范。重要动作追加 RUNLOG，阶段进度只更新 STATUS，细节写工作卡。工具/安装包/压缩包与预编译固件继续遵守本地保留规则。

## 每次交付格式

- 本次完成：子任务、修改文件和实际行为。
- 验证证据：实际命令/方法、版本、退出码或实测结果、文件路径与证据范围。
- 判定：按冻结规则逐条给出结果；探索只给观察，缺失项不当作通过。
- 未完成：具体缺少什么、阻塞哪项、哪些工作仍可继续。
- 下一步：一个可直接执行的子任务及其所需输入。

## 为什么细化到这个程度

按“能独立实现、能验证、能定位失败”的边界拆分。例如 G01 的采集代码、串口记录、实物标定和独立验证可分别推进；不能用一条“完成测量”掩盖四者差异。函数名、接线和具体阈值应在读过当前代码与实物记录后确定，写入工作卡或统一规范，避免长期提示词随着实现变化而失效。
